# Amendment 2 to the Commonplace Monotonic Log 0.1-draft: Entry v2 Operation ID

**Date:** 2026-08-25
**Status:** In force (ruled by jes 2026-08-25 19:15Z: 'yep, v2 persist')
**Amends:** `docs/commonplace-monotonic-log-spec.md` (0.1-draft, 2026-08-21). The original spec file is preserved byte-identical for provenance; this amendment states the deltas. A merged later-version text may follow at jes's direction.

**Ruling refined:** 2026-08-25 19:15Z: “yep, v2 persist”; 2026-08-25
19:48Z, asked required or optional: “required”.

## Normative changes

1. **Entry versions.** Entry `version` MAY be `1` or `2`. Version 1 is unchanged, byte for byte, including `extra_top_level_field` for any ninth key.

2. **Version 2 shape.** Version 2 has the eight version-1 fields plus ONE REQUIRED top-level field `operation_id`: a non-empty JSON string, at most 256 UTF-8 bytes, opaque to the log (never parsed, never compared across writers). Everything else about v2 is identical to v1: same I-JSON constraints, same 1 MiB canonical cap, same canonicalization (RFC 8785 key order puts `operation_id` between `log_id` and `prev_entry_id`), same merge classification — bytes are bytes; a v1 and a v2 entry may share a writer lane.

3. **Version 2 rejection.** A v2 entry with any OTHER extra key is `extra_top_level_field`. A v2 `operation_id` that is absent, empty, non-string, or over 256 bytes uses reason slug `invalid-operation-id` under code `invalid_entry`.

4. **Semantics.** `operation_id` is the caller's idempotence key, carried so that a reader replaying the log can derive the set of operations already applied without a second store; the log itself does not enforce uniqueness of it — coordinate occupancy and derived entry ids remain the only mechanism (spec §9, DocumentProfile).

## Reversal recorded

The `Commonplace.Log.DocumentProfile` moduledoc records this accepted limitation:

> ACCEPTED LIMITATION, not an oversight: if no earlier attempt landed,
> reuse cannot be detected at all, because nothing exists to conflict
> with and the closed eight-field entry cannot carry an operation ID —
> `extra_top_level_field` is a validation error, so it could only live in
> `body`, which this layer must not interpret. Detection therefore covers
> exactly the cases that could corrupt history and no others. This cost
> was named before the choice was made and was accepted deliberately in
> preference to a durable registry with a retention policy.

Jes knowingly reversed that accepted limitation on 2026-08-25 at 19:15Z with
the ruling “yep, v2 persist”. This amendment adds the versioned canonical field;
the existing DocumentProfile paragraph remains in place for Amendment 2
provenance and will be amended when DocumentProfile begins emitting v2 entries.

## Unchanged

All version-1 entry bytes and validation behavior, I-JSON constraints, the
1 MiB canonical-entry cap, RFC 8785 canonicalization, invariants, store
operations, merge classifications, synchronization, wire protocol, failure
semantics, and security boundaries remain unchanged except for the explicit
version-2 entry-shape delta above.

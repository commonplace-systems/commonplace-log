## Outcome

The backup walks registered realms, enumerates their logs through the newly
authorized `/list-logs` read route, and copies immutable entries under
`realm/log/writer/sequence.json`. Each log frontier is committed after its entries;
the realm manifest follows all its log frontiers. A run log records coverage,
counts, checkpoint writes, and named stops without copying credentials or remote
error bodies. The production backup entry has only `scheduled()`. Its local test
entry alone exposes the HTTP trigger.

The full worker suite passed **319 tests across 24 files**, seed **20260905**.
The nine backup runtime tests and two deployment/source tests are included in that
total. The focused TypeScript check passes. The full TypeScript check still fails
with exactly the two inherited TS2307 diagnostics; no new diagnostic remains.

## Failed development runs retained

The first focused run had two failures because `listLogs()` queried a nonexistent
`logs` table in a realm with no logs. The fix reads `sqlite_master` and returns an
empty inventory without initializing tables; the test checks both properties.
See the complete `focused.log`.

After that repair, an A3 run passed its assertions but failed isolated-storage
teardown, and prevented later tests from running:

```text
Failed to pop isolated storage stack frame in test/backup/backup.workers.test.ts's test "A3: second mint is 409; revoke stops only that realm and names the stop in the persisted run log".
In particular, we were unable to pop Durable Objects storage.
```

The full runtime error and stack are retained unabridged in `focused-final.log`;
the diagnostic included `Expected .sqlite, got ...sqlite-shm`. The backup client
had not drained non-success response bodies. After draining those streams before
returning named stops, the focused suite and the complete suite passed. This is
reported as a resource-lifetime fix with observed results, not dismissed as an
environmental failure. The full suite also prints existing workerd/header warnings;
they remain visible in its unabridged log.

## Declared files and limits

Beyond new files under `worker/`, the approved route touches exactly
`src/realm/store.ts`, `src/realm/http.ts`, and one READ_ROUTES line in
`src/realm/realm_auth.ts`. Test discovery and typechecking need three existing
configuration edits: `vitest.config.ts`, `tsconfig.json`, `tsconfig.workers.json`.
These include the new project and keep its Workers-runtime tests out of the Node
project. Existing tests and their expectations are unchanged. Design §9 and this
report/evidence are the documentation additions. See `implementation-files.txt`
and `status-before-report.txt` for the enumerated paths and Git status.

The KV interface exposes only `get` and `list`. Installed Wrangler's KV binding
schema has `binding`, `id`, `preview_id`, `remote`, and disallows extra properties;
there is no read-only switch. This implementation establishes a code restriction,
not platform attenuation of arbitrary replacement Worker code. The report and
README make that distinction explicit for review.

The new production config contains a placeholder for the existing registry ID.
Before activation, that binding must be configured and the deployed source SHA
must be checked to include the new route. No credentials were sought and no
production completeness, latency, or cross-script runtime claim is made here.
Registry reconciliation/backfill is 1b-iii; pre-registry realms remain omitted.
This is a collection of per-log snapshots, not an atomic realm snapshot. Restore
by identical `entry_id` is 1c and remains unverified; D5's overall durability claim
cannot be inferred solely from this round's passing tests.
